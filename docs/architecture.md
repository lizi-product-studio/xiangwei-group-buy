# 社区团购架构

系统只有一个社区团购领域。API 服务按能力拆分为认证与员工、目录与团期、订单、支付退款、配送领取、通知、账本和审计；领域服务只依赖所需的窄存储能力。

## 关键一致性

- 订单创建在同一事务中锁定团期可售量、写订单明细和幂等记录。
- 支付回调以事件号和正文摘要去重，订单支付与取消/截单通过条件状态更新竞争。
- `REFUNDING` 转换与唯一退款义务（固定 `providerRefundNo`）在同一数据库事务持久化；退款调和扫描只消费已提交的义务，绝不以事务外数组或内存 Promise 首次创建退款。
- 退款提交使用租约和认领令牌，迟到的支付机构响应不能覆盖新处理者。退款记录必须表达待提交、提交结果未知、支付机构处理中、可重试失败、人工挂起和成功这六种逻辑状态（可由状态与重试/租约字段等价表达）。
- 调和以同一 `providerRefundNo` 查询或安全重提：提交前失败可重试；提交后响应丢失先查询；未找到、5xx 或超时在租约到期后按退避重试，到达上限转人工处理而非永久停留在处理中。全额和部分退款使用同一恢复语义；成功落账、订单/支付状态变更和迟到回调均为一次性条件更新。
- 到货差异先保存现场事实，再按 `paidAt ASC, orderNo ASC` 生成草案；运营确认后才开放正常数量领取并允许财务退款。
- 核销以领取请求号和内容摘要幂等，订单明细在事务内更新，支持分次领取。
- 通知使用事务内 outbox，提供方失败重试后进入人工联系队列。
- 员工状态和点位范围在每次敏感操作校验；变更时删除现有会话。

## TASK-REM-P0 验收契约

- 退款故障恢复必须可重放：事务提交后、外部提交前的进程中断，重启调和后应只创建并提交原退款义务一次；支付机构收到请求但响应丢失时，调和只能使用原退款单号查询/重提。
- 到货确认入口按角色和点位范围二次校验，不能只依赖前端隐藏。`PICKUP_MANAGER` 有已授权点位的正常提交权，`OPERATOR` 没有该权，`SUPER_ADMIN` 的紧急代办必须有原因并进入审计。

## 数据基线

当前未正式生产且没有需要保留的支付、订单、退款或结算数据，因此迁移已重建为 `0001_community_baseline.sql`。迁移不写入演示数据，也不写入任何具体城市或点位。应用状态由 MySQL InnoDB 单行聚合锁保证跨实例原子性；Redis 负责团期生命周期任务。

部署到曾运行旧结构的数据库时，必须新建空数据库并执行新基线，不得让部署脚本自动删除未知表或外部数据。

应用启动不得生成“全国默认自提点”或任何伪履约数据；消费者公开区域必须至少关联一个真实启用点位。
