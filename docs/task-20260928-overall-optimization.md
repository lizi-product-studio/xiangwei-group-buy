## 核心判断：县域的瓶颈是“数据累积”，不是“并发”

- 全部业务状态存于 MySQL 单行 JSON。每个请求读取时都要把整份 JSON 解析成完整内存对象，写入时整份重写。
- 因此成本主要随**历史数据总量**增长，而不是随同时在线人数增长。并发低可以延后行级锁、多副本等改造；但订单、会话、通知、审计每天都在累积，即使并发很低，读写也会越来越慢、越来越占内存。
- 已有证据：合成数据 1000 用户 / 1 万订单时 payload 8.4 MB；仅 10 RPS 公开请求下，进程内存峰值约 450 MiB（`docs/evidence/readiness-20260908/capacity-after-auth.json`）。API-only 部署编排 `infra/compose.host-api.yaml` 限制容器 384 MiB、V8 堆 256 MiB（推断为正式机当前方式，待核实）。**内存会先于 CPU 和并发成为约束**，超限表现为 OOM 重启。
- 合成订单只有一个商品，没有支付、账本、通知、领取记录、审计；真实订单单笔体积应明显更大（推断）。所以必须先实测正式机的真实体积与增速，再校准下文触发线。

## 规模假设与结论（2026-09-28 用户补充）

用户估计短期 30–50 个点位，单量需看实际情况，无法预估。按首测校准的单笔 4–6 KB（取 5 KB）推算：

| 点位 × 每点日均单量 | 日均订单 | 日增量 | 当前架构到 4 MB 红线 |
|---|---|---|---|
| 30 × 3（很保守） | 90 | 约 0.45 MB | 约 9 天 |
| 30 × 10 | 300 | 约 1.5 MB | 约 3 天 |
| 50 × 10 | 500 | 约 2.5 MB | 约 2 天 |
| 50 × 30 | 1500 | 约 7.5 MB | 不到 1 天 |

- 结论不依赖单量预估：30–50 个点位下，即使每点每天只有 3 单，当前单行 JSON 也会在 1–2 周内超出红线。**规模化开团前，必须完成按实体分表**，只拆日志类数据（原 B 档）不够，订单、明细、支付、通知本身就是主要增量。
- 冷热归档也不够：订单从下单到领取截止、售后结束约需一周，活跃期内的订单都要常驻。每天 500 单时，活跃数据约 3500 单 × 5 KB ≈ 17 MB，仍超红线。
- 并发确实不是问题：每天 1500 单、晚间高峰一小时集中 30%，也只有约 0.13 单/秒。所以分表后**保留全局串行锁**即可，行级锁和多副本可以继续延后。这样把“数据量”和“并发”两个问题拆开，前者必须现在解决，后者按扩张再说。
- 在分表上线前，现有架构只用于**小范围试点**，见「试点闸门」。

由主编排在用户同意后，用已授权连接对正式库执行只读查询，每周一次；试点开团后改为每日，并在扩点位前后各加测一次。结果追加到本文件「监测记录」。

       JSON_LENGTH(payload, '$.orders')                        AS orders,

       OCTET_LENGTH(JSON_EXTRACT(payload, '$.lines'))          AS lines_bytes,
       OCTET_LENGTH(JSON_EXTRACT(payload, '$.sessions'))       AS sessions_bytes,

       OCTET_LENGTH(JSON_EXTRACT(payload, '$.audits'))         AS audits_bytes,
       OCTET_LENGTH(JSON_EXTRACT(payload, '$.callbacks'))      AS callbacks_bytes,
       OCTET_LENGTH(JSON_EXTRACT(payload, '$.idempotency'))    AS idempotency_bytes,

同时记录 API 容器内存峰值与重启次数（`docker stats --no-stream`、`docker inspect -f '{{.RestartCount}}'`）。据两次记录计算日增量与“到达下一档的预计天数”。

### 试点闸门与触发线

阈值由“8.4 MB 时进程内存约 450 MiB、超出 384 MiB 限制”保守外推，属于推断值；首批真实团期后由主编排校准并记录依据。B 档（分表）上线前，按下表控制试点规模；B 档上线后本闸门失效，改用 B 档自身的容量验收结果。

| 档位 | 条件（满足任一） | 动作 |
|---|---|---|
| 绿 | payload < 2 MB，且容器内存峰值 < 250 MiB，无 OOM 重启 | 允许试点，**启用点位不超过 5 个**；试点期间 M-01 改为每日 |
| 黄 | payload 2–4 MB；或按近 7 天增速预计 14 天内到 4 MB；或容器内存峰值 250–300 MiB | 不再新增点位；B 档最高优先级 |
| 红 | payload > 4 MB；或容器内存峰值 > 300 MiB；或出现 OOM 重启；或用户反馈核销/下单明显卡顿 | 暂停新开团期，已开团期正常履约；B 档上线后恢复。宿主机仅约 1.9 GiB 内存，调高容器内存只能经用户批准作短期缓冲，不视为解决 |
| 扩张 | 覆盖第二个县或多区域；高峰下单持续 > 5 笔/秒；需要多副本 | 启动 C 档 |

黄档和红档的限制属于经营决定，由主编排报告数据，用户确认后执行。

#### A2 认证链路单快照（P-02）

#### A4 聚合体积自动告警

- 范围：`apps/api/src/modules/core/mysql-store.ts`、`/health/reconciliation` 或日志、相关测试。

### B 档：按实体分表、保留全局串行锁（规模化开团前必做）

目标：消除“每个请求加载全部数据”，使单次读写成本与历史总量脱钩；并发模型保持不变。

- 拆分范围：所有随用户、订单、时间增长的集合都移出聚合行，包括用户、隐私同意、会话、改密令牌、幂等键、订单、订单明细、结算批次、支付、合并支付、支付回调、整单退款、部分退款、账本、审计、通知、通知偏好、领取凭证、领取窗口、领取记录、到货确认、履约异常、分配、分配草案、取消申请、品质售后、区域意向，以及团期与配送计划（每点每期一条，会持续增长）。
- 保留在聚合行：区域、点位、商品、分类、首页横幅、员工、角色、点位授权等配置类小数据。
- 表结构建议（设计稿可调整）：每个集合一张“文档表”，主键 + 业务 JSON 文档 + 查询所需的索引列（如 `user_id`、`campaign_id`、`order_id`、`pickup_point_id`、`status`、`created_at`、`expires_at`、`next_attempt_at`）。比完整关系建模工作量小，适合当前规模；以后需要时再逐表改为关系列。
- 并发：每个写事务开头仍对聚合行 `SELECT … FOR UPDATE`，作为全局串行锁；事务内按需读写各表，提交时只写改动的行。语义与现状一致，不引入新的竞争条件。按县域单量，全局串行的吞吐足够。
- 读取：按需查询索引，不再加载整份快照；只读请求不加聚合行锁。
- 工作量提示：`CommerceStore` 接口约 196 个方法，目前 MySQL 实现复用内存实现、依赖整份快照。B 档需要为这些方法逐一提供按表实现，是本方案最大的一项，须由工程执行端到端负责。
- 一致性保障：把现有 store 行为整理成一套“存储契约测试”，同时跑 `MemoryStore` 与新 MySQL 实现；现有 API 测试在真实 MySQL 下强制执行。
- 迁移：前向迁移用 `JSON_TABLE` 从聚合行逐集合抽出数据并校验条数与关键金额合计（订单金额、支付、退款、账本借贷）前后一致；可重复执行、可中断重跑；写明 DDL 隐式提交的中间状态处理。迁移前完成 O-07 备份恢复演练，并保留整行快照备份作为回退依据。
- 容量验收：改造合成数据脚本，使订单包含支付、账本、通知、领取记录，接近真实体积；在测试机按“50 点 × 30 单/日 × 90 天历史”造数，验证容器内存峰值 < 300 MiB、下单与核销 p95 < 500 ms、零 OOM。阈值可由用户调整。
- 流程：设计稿 → 主编排审阅 → 用户批准正式迁移窗口 → 实施 → 独立审核 → `pnpm check` 与全量 E2E → 测试机迁移预演与容量验收 → 正式迁移。
- 分步交付（可选）：若开团时间紧，设计稿可提出按集合分批迁移（先审计、会话、通知，再订单与支付），但每批都要单独迁移、验收和审核。设计稿须说明分批与一次迁移的取舍。
