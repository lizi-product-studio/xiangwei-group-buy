# 产品反思记录：人员创建、权限与导航闭环缺失

**日期：** 2026-08-14
**范围：** 运营后台、点位负责人、核销与权限配置

## 1. 发现的问题

当前“核销员授权”页面要求运营人员手工输入一个“核销员用户 ID”，同时系统没有提供员工创建、员工目录、账号激活、角色选择、点位绑定或离职停用入口。

这不是一个小的交互瑕疵，而是一个不可用的业务断点：

> 平台不知道从哪里创建核销员，核销员也不知道从哪里得到 ID，运营人员无法安全地完成授权。

截图中的说明“核销员从其受控账号资料中提供 ID”把系统内部实现细节转嫁给运营者。它既不能保护消费者资料，也不能支持真实的人员管理。

## 2. 我此前的错误判断

1. **把“权限分配”误当作“人员管理”。**

   我只考虑了已有账号如何绑定点位，却漏掉账号必须先被创建、激活、日常维护和停用的前置链路。

2. **错误地把最小化展示理解为不提供员工目录。**

   不展示消费者数据是正确的；但员工目录可以只展示员工姓名、脱敏手机号、角色、状态和点位范围。以隐私为由要求输入不可读 ID，是错误的产品取舍。

3. **按技术模块组织后台，而不是按工作任务组织后台。**

   商品、团期、配送、自提点、核销员授权和操作记录被拆散或混放，导致运营者无法按“先建人、再配点、最后核销”的顺序完成工作。

4. **在角色生命周期未闭环前，过早下发了页面改造任务。**

   我此前给出的导航方向没有先通过“创建 → 授权 → 使用 → 停用”的走查，因此没有在第一时间发现“自提点负责人从哪里来”。

## 3. 对业务的影响

- 新开一个自提点时，无法独立完成负责人入职和授权。
- 运营人员可能转而共用管理员账号，造成越权、无法审计和离职后权限残留。
- 手工传递用户 ID 容易填错，且不具备可理解性。
- 自提点负责人无法获得与自己职责匹配的工作台，容易进入不该看到的运营页面。
- 这一断点会让“提货码核销”看似存在、实际无法部署到真实点位。

## 4. 根因与今后的强制检查

今后凡是涉及“谁能做某件事”的功能，产品设计必须先完成以下四段闭环，缺一不可：

| 阶段 | 必须回答的问题 | 本次遗漏 |
|---|---|---|
| 创建 | 谁创建人员？填写什么？账号如何激活？ | 漏掉 |
| 授权 | 赋予什么角色、哪些点位、何时生效？ | 仅实现了片段 |
| 使用 | 登录后看到什么？能做什么？看不到什么？ | 不完整 |
| 回收 | 离职、换点、暂停时如何立即撤权并留痕？ | 漏掉 |

以后在把需求交给研发前，必须完成这三项检查：

1. **角色走查：** 用平台负责人、运营、自提点负责人、客服、财务分别从登录开始做一遍核心任务。
2. **零手工 ID 检查：** 面向业务人员的页面不得要求输入系统内部主键、数据库 ID 或接口参数。
3. **权限反向检查：** 除了“谁可以做”，还必须写清“谁绝对看不到/做不了”，并由服务端测试验证。

## 5. 本次纠正决策

- 不再使用“核销员 ID 授权”作为运营流程。
- 增加“员工与权限”能力：创建员工账号、选择角色、绑定自提点、激活/停用、重置初始凭据和审计。
- 将核销职责并入“自提点负责人”这一业务角色；它不是一个脱离人员管理的孤立 ID。
- 自提点负责人登录后只进入“点位工作台”，不显示商品、团期、成本、财务和其他点位数据。
- 导航、页面、服务端权限和测试必须共同实现；仅在前端隐藏菜单不算完成。

## 6. 验证承诺

该问题只有在以下场景均通过后才可关闭：

1. 平台负责人无需知道任何内部 ID，即可创建一名点位负责人并绑定自提点。
2. 负责人首次登录后仅能看到自己的点位工作台。
3. 负责人可确认到货、查询/核销提货码、登记现场异常；不能读取其他点位、成本、团期配置、退款或财务信息。
4. 平台负责人停用该账号或解除点位绑定后，既有登录会话立即失去对应权限。
5. 上述创建、授权、变更、停用和核销动作都有可查询的操作记录。
