# TASK-REM-P1-B 实际履约主流程验收契约

本文件只定义 P1-B 的装袋标签、分次领取、到货差异退款和逾期领取闭环。不改变 P0 的退款恢复与到货权限契约，也不包含通知、意向、审计扩展或商品生命周期（P1-C）。PRD、README 和架构说明优先于本文件。

## 角色 × 页面 × 动作

| 角色 | 页面 | 可见事实与动作 | 明确禁止 |
| --- | --- | --- | --- |
| `OPERATOR` | 团期管理 | 已锁单团期生成并打印/导出装袋标签 | 未截单、无合格已付款订单的标签动作 |
| `SUPER_ADMIN` | 团期管理 | 与 OPERATOR 相同的标签读取能力 | 通过普通点位工作台绕过点位范围 |
| `PICKUP_MANAGER` | 我的点位工作台 | 仅已授权、已到货点位的订单查询与分次核销 | 跨点位、超量、逾期、零数量核销 |
| `CUSTOMER_SERVICE` | 售后与异常 | 查看已有授权范围内的履约异常 | 财务退款、逾期延期或报损 |
| `OPERATOR` | 售后与异常、领取窗口 | 查看履约异常；对 `EXPIRED_PENDING` 延期、登记退款/报损 | 财务执行退款 |
| `FINANCE` | 财务管理、领取窗口 | 查看履约异常；仅对 `REFUND_CONFIRMED` 执行差异退款；仅对 `REFUND_PENDING` 执行逾期退款；查看退款与账本 | 延期、报损、未批准异常退款 |
| `SUPER_ADMIN` | 财务管理、领取窗口 | 可执行已批准退款；可执行运营的逾期延期/处置 | 在点位工作台作为普通负责人核销 |

所有前端可见性均是体验边界；API 继续按角色、状态、订单归属和点位范围最终拒绝。
当前已批准的员工授权模型只为 `PICKUP_MANAGER` 持久化点位范围；因此
`CUSTOMER_SERVICE` 与 `OPERATOR` 的“已有授权范围”是其既有的全局售后/运营队列，
不在本任务中另造点位授权模型。领取核销始终要求点位负责人自己的已授权点位。

## 状态与前后台闭环

### 装袋标签

截单后，`LOCKED`（及履约中的既有等价状态）团期的合格已付款订单可由 OPERATOR/SUPER_ADMIN 读取标签。已领取或已完成、但并未退款的订单仍保留同一装袋事实，允许只读重打/导出；退款订单不在结果中。标签稳定按 `paidAt ASC, orderNo ASC` 排序，并包含订单号、自提点和逐商品名称/数量。未付款订单不在结果中；读取与重复导出没有业务写入。页面必须具有加载、空结果、失败/重试和不可用状态。

### 分次领取

点位负责人先在已授权、已到货点位按订单号查询，再以六码取货码提交领取请求。每项本次数量为 `0..remainingPickupQuantity`，且总计至少一项大于零；提交前展示本次复核，提交中禁用。服务端领取请求号与内容摘要保证幂等：首次部分领取减少剩余量但不关闭凭据，全部领取才关闭凭据并完成订单。错误码/状态包括跨点位、旧或无效码、过期、超量、零数量与重复请求。

### 到货差异退款

运营确认差异后，履约异常进入 `REFUND_CONFIRMED`；只有 FINANCE/SUPER_ADMIN 可以填写必填退款确认说明并二次确认后执行该异常的部分退款。异常页面显示订单、异常类型、逐商品数量、可复算金额/金额快照和运营确认说明。执行成功或支付机构仍处理中时都重取异常、退款与账本；同一异常重复执行必须由既有退款事实收敛，账本成功只写一次。非 `REFUND_CONFIRMED` 不显示操作且 API 保持 403/409。

### 逾期领取

领取窗口事实显示订单、点位、截止时间、状态和下一责任角色：

```text
ACTIVE / EXTENDED --到期--> EXPIRED_PENDING
EXPIRED_PENDING --OPERATOR/SUPER_ADMIN 延期（仅一次，新的未来截止）--> EXTENDED
EXPIRED_PENDING --OPERATOR/SUPER_ADMIN 退款登记--> REFUND_PENDING
EXPIRED_PENDING --OPERATOR/SUPER_ADMIN 报损登记--> LOSS_RECORDED / CLOSED
REFUND_PENDING --FINANCE/SUPER_ADMIN 执行退款--> CLOSED
```

延期、退款登记和报损均需原因；非法状态不展示动作。FINANCE 不得执行延期/报损，OPERATOR 不得执行财务退款。退款使用已有部分退款恢复语义，幂等且账本成功只写一次；报损撤销普通领取凭据并使订单不再悬挂在 `READY_FOR_PICKUP`。

## UI 状态与响应式

每个新工作区必须有 loading、空、错误/重试、禁用和无权限反馈。375、768、1440px 下不出现页面级横向滚动，表格仅在自身容器内滚动；输入、复核/确认弹窗与主操作保持可触达。

## 验收证据

1. OPERATOR 从网页在锁单且有已付款订单的团期生成标签；断言稳定顺序、订单/点位/商品数量和未付款订单排除。
2. 已授权 PICKUP_MANAGER 以真实 UI 对同一订单分两次领取；第一次后剩余量刷新，第二次完成；零数量、超量、跨点位、旧码与重复请求有正反例。
3. 真实差异到货和运营确认后，FINANCE 从网页填写说明、二次确认并执行一次退款；异常、退款、账本重取后一致。OPERATOR/CUSTOMER_SERVICE 无财务按钮且 API 拒绝。
4. 边界到期、一次延期、退款职责分离、报损关闭、重复退款与账本一次性均有 API/单元测试；浏览器从角色页面完成操作。
5. 浏览器监听未预期 4xx/5xx、`pageerror`、`requestfailed`；保留 P0/P1-A 全量回归。真实 MySQL/Redis 未提供连接时必须 fail-closed，标记 BLOCKED 而非 PASS。
