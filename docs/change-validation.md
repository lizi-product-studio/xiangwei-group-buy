## 实施方案

1. 小任务默认一名写入者直接完成；完整多人闭环只用于已启用独立审核的任务。原始验收与必要修复优先，非阻塞关联问题单列，禁止无依据扩大重构。
2. Quality 从串行全量任务改为影响识别、包检查、浏览器、应用镜像、统一结果。包检查、浏览器和镜像使用独立 runner 并行；浏览器内部仍保持单 worker，不能在同一测试数据上并行多个写入用例。
3. 带覆盖率运行替代先普通单测再重复覆盖率测试；生产编译由受影响 Dockerfile 验证，避免此前 pnpm check 内先 build、随后 Docker 再 build。共享包因类型和运行依赖仍须构建；没有降低覆盖率阈值或关闭集成测试。
4. 只构建受影响镜像，利用 GitHub Actions 构建层缓存；较新提交取消同一事件、同一分支的过期 CI。没有将缓存镜像自动视为生产发布包，也没有变更部署方式。

## CI 路由

| 累计改动 | 包检查 | 浏览器 | 镜像 |
|---|---|---|---|
| 根 AGENTS.md、README.md、docs 下 Markdown | 无业务检查；仍执行分流回归和统一结果 | 无 | 无 |
| 后台源码/资源/配置 | 后台类型、覆盖率；源码 lint | 全套现有浏览器用例 | 后台 |

| 仅浏览器测试/配置 | 浏览器代码 lint 与类型 | 全套现有浏览器用例 | 无 |
| 仅应用单测文件 | 对应包检查 | API/后台仍跑浏览器 | 无 |

混合改动取并集。小程序 package.json 也按全量处理，因为依赖安装与 API Dockerfile 使用各工作区 manifest。没有对页面内部做脆弱的文本分析来猜测“仅文案”；后台一处变化仍跑后台包及现有浏览器回归。

## 不漏验的边界

- push 从同分支最近可用的成功 Quality push 祖先起算；PR 从目标分支成功 push 祖先起算并检查合并结果。取最近100条成功记录中的可用祖先，找不到、历史不完整或 API 查询失败均走全量。手动 workflow_dispatch 始终全量。
- 不使用 push 的 before 作为成功证明。上一提交失败/取消/未跑完，下一次只改文档或测试，仍包含之前未验证的业务改动，不能跳过它们。
- 删除计入原路径；移动按删除和新增分别计入，不能把业务代码移动到 docs 后变成文档豁免。
- 最终 required check 保留 job id/name `verify`。所有计划中的任务必须 success；意外 skipped、failed、cancelled、缺失结果均不通过。证据上传失败只影响证据可用性，不能掩盖测试失败。
- CI 自身、影响分类器和未知文件变更强制全量。本次机制变更第一次远端运行因此预期全量，这是机制验收，不代表今后普通修改也全量。
