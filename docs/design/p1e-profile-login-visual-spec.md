## 1. 结论与适用边界

本规格补齐以下三个同视口状态，并作为 TASK-REM-P1E 前端视觉实现的唯一输入：

1. 独立登录页：从批准游客态的橙色主操作、绿色隐私提示、白色圆角卡片和米白页面背景做最小派生。
2. “我的”游客态：严格保持批准原型的登录卡、订单入口、固定自提点、常用服务和底部导航层级；常用服务内容同时服从现有产品基线，保留已有五项并补充“隐私与协议”。
3. “我的”已登录态：仅把登录卡替换为同尺寸体系的身份卡，并增加订单数字摘要与退出登录；其余结构沿用游客态。

本规格只定义视觉、展示层级、组件状态和可用性，不改变登录方式、协议拦截、auth intent、30 分钟 TTL、取消 suppression、session epoch、401 / logout 清理、写操作不自动重放或任何订单、支付、点位、配送与售后规则。

现有 Figma 原文件状态为 `BLOCKED`：仓库、任务文档与证据目录均未发现可访问的 Figma URL、file key 或 node id。因此未创建或伪造 Figma 页面；本地高保真画面和本文档是本轮批准载体。该阻塞不影响按任务约定走本地规格降级交付。

## 5. 三个状态的页面规格

### 5.1 独立登录页

信息顺序固定为：原生返回与标题 → 品牌标记 → 标题 / 来源说明 → 登录确认卡 → 正式微信登录 → 本地开发登录（条件显示）→ 协议同意与链接 → 暂不登录返回。

- 品牌标记：`66 × 66 px` 橙色圆形，内置白色微信图标。该标记是从批准按钮做的最小品牌派生，用于替换旧稿“乡”字方块。
- 正式主操作：橙色胶囊按钮，宽度为卡片内容宽度，高 `46 px`。在任何环境中都不得出现另一个同级正式主按钮。
- 开发体验登录：位于浅绿提示区内，白底橙色描边，高 `40 px`；只有 `develop + local HTTP + demo` 同时满足时出现。
- `trial / release / wechat / HTTPS / 未知环境`：整个开发提示区与开发体验按钮均不渲染，不能只做禁用或隐藏文字。
- 协议：按钮下方显示可点击的同意控件、协议版本和两个协议链接；截图展示“已同意”基准态，不表示可默认替用户同意。实际初始值和版本逻辑继续服从 P1D。
- 取消返回：中性描边按钮，高 `43 px`，与主操作至少间隔 `13 px`。AUTHENTICATING 期间服从现有逻辑禁用。

#### 登录组件状态

| 状态 | 视觉 | 行为边界 |
|---|---|---|
| 默认 / 未同意 | 同意控件为空；主按钮保持可见 | 点击主按钮只显示协议行下方错误，不发起登录 |
| 协议错误 | `#B44732`、`12/18 px`，紧跟协议行；不使用 toast 作为唯一反馈 | 用户勾选后错误立即消除 |
| AUTHENTICATING | 主按钮文字“登录中…”；白色 `LoadingOutlined` 旋转；按钮不透明度 `0.66`；主、开发、取消均不可重复点击 | 不改变 P1D 状态机，不并发发起第二次认证 |
| ERROR | 登录确认文案下方出现 `#FFF1EC` 错误块，圆角 `8 px`，内边距 `10 × 12 px`；主按钮文字“重新登录” | 保留协议状态与返回能力；不得吞掉错误或只改按钮颜色 |
| 取消授权 | 作为可恢复错误显示“未完成微信授权，可重新登录或暂时返回” | 不循环拉起授权，不自动重放原写操作 |
| 正式环境 | 不显示本地开发区 | 必须 fail-closed，正式登录仍只有微信快捷登录 |

错误块可增高页面，独立登录页必须纵向滚动；错误文案不得覆盖取消返回。协议链接、复选控件、主按钮和返回操作均需支持键盘焦点 / 屏幕阅读器可识别名称。

### 5.2 “我的”游客态

以下结构、顺序和主要文案来自批准原型，不得重新组织：

1. 登录卡：游客头像、登录价值说明、橙色微信快捷登录、绿色隐私说明。
2. 我的订单：全部订单入口；待付款、进行中、待自提、退款售后四入口。游客点击受保护订单入口时走现有 auth intent。
3. 我的固定自提点：标题、切换入口、绿色位置图标、未选择状态和地址 / 营业时间占位。游客可直接进入点位选择，不得把整卡改成登录阻断。
4. 常用服务：按当前产品基线顺序保留“订单消息、开通意向、客服、帮助、关于”，并在末尾补充原型要求的“隐私与协议”，共六项。辅助文案分别为“地点、发车与到货提醒”“所在区县暂未开放？登记需求”“联系在线客服”“下单与集中领取说明”“版本与平台信息”“隐私政策与用户协议”。
5. 底部导航：团购、购物车、订单、我的；“我的”为橙色选中态。

六项服务每行保持 `45 px` 视觉高度和不小于 `44 × 44 px` 的触控热区。390 × 844 顶部截图无需同时露出最后两项，但页面必须可滚动到底；滚动到底时“关于”“隐私与协议”完整可见，最后一行与固定底栏之间保留至少 `16 px`。

#### 本轮实机尺寸复核（仅常用服务）

证据为 `.visual-audit-2026-08-27/profile-fidelity/iteration-2/01-actual-profile-size-issue.png`，并已归一为 `.visual-audit-2026-08-27/profile-fidelity/design/reference/iteration-2-actual-profile-390x844.png`。在同一 `390 × 844 px` 视口中，实机常用服务卡外框已经接近页面可用宽度，但标题下方六行入口与分割线被压在约 `181 px` 的居中窄列内，形成“卡片全宽、列表半宽”的不一致。该结论来自截图像素采样，属于尺寸 / 容器问题，不是图标、字号、颜色或文案问题。

目标是让六行入口和分割线充分使用服务卡内容宽度：服务卡仍沿用页面左右 `12 px` 留白与现有内边距，行本身必须从内容区左边缘拉伸到右边缘；不得为了消除滚动而缩小行高、文字、图标或触控热区。390 px 下服务卡内容区约 `338–342 px`（随边框取整），不是固定的 `50%` 或居中窄列。

研发可直接按下列 profile-only 样式边界修复（数值与现有 token 对齐）：

```css
.service-card {
  width: 100%;
  max-width: none;
  box-sizing: border-box;
  padding-inline: 26rpx;
}

.service-card > .service-row {
  display: grid;
  width: 100%;
  max-width: none;
  min-height: 90rpx;
  margin-inline: 0;
  align-self: stretch;
  box-sizing: border-box;
  grid-template-columns: 44rpx auto minmax(0, 1fr) 26rpx;
  column-gap: 14rpx;
}
```

当前仓库快照的 `apps/miniprogram/src/pages/profile/index.wxss` 已出现 `width: 100%` 与四列网格声明，但该声明在 iteration-2 实机画面中没有生效；研发应先确认开发者工具加载的是最新编译产物、样式作用域没有被覆盖，且不存在旧缓存或窄包装器，再做最小覆盖。不得仅凭源码已有声明判定尺寸问题已关闭。

必须移除或覆盖任何作用于服务行 / 列表包装器的 `width: 50%`、固定 `max-width`、`margin-inline: auto`、窄宽度 `align-items: center` 或同等约束；分割线跟随 `.service-row` 的 `width: 100%`，不得单独保留半宽。保持标题 `30rpx / 42rpx`、标题内边距 `22rpx 0 14rpx`、行最小高度 `90rpx`（视觉约 `45 px`）、分割线 `2rpx`、服务图标 `44rpx`、箭头 `26rpx`、主文案 `25rpx / 36rpx`、辅助文案 `21rpx / 30rpx` 与现有图标资产不变。

在 `320–430 px` 宽度范围，服务卡与服务行始终 `width: 100%`、`max-width: none`，不产生横向滚动；页面留白保持 `12–16 px`。小于 `360 px` 时只采用现有紧凑列规格（图标 `40rpx`、列间距 `10rpx`、主文案 `23rpx`、辅助文案 `19rpx`，行高仍不低于 `88rpx`），不得把服务列表改成两列、截断入口名称或继续居中压窄。动态辅助文案可省略号，入口名称必须完整可读。

六项服务继续承载预期的纵向滚动。滚动到底时“关于”“隐私与协议”整行可见，最后一行下沿与原生 tabBar 上沿至少相隔 `16 px + safe-area-inset-bottom`；不得用负外边距、固定遮罩或改变 tabBar 来伪造间距。研发本轮只能修改 `apps/miniprogram/src/pages/profile/index.wxss` 中服务卡 / 服务行及其 `@media` 规则；若现有 DOM 确实存在额外窄容器，最多调整 `apps/miniprogram/src/pages/profile/index.wxml` 的服务行包装层，不得改动文案、路由、绑定、认证、订单、点位、tabBar 或其他页面。该复核不改变既有橙 / 绿品牌映射、登录页、身份卡或头像规则。

游客态不显示退出登录、账户手机号、会员、积分、优惠券或开发体验入口。开发体验登录只存在于独立登录页。

### 5.3 “我的”已登录态

已登录态是游客态的最小派生：

- 登录卡替换为身份卡，保留白卡、边框、圆角和相同页面节奏。
- 身份卡显示现有头像 / 头像兜底图、现有 `userName`、身份可见性说明；不得显示手机号或新增账号字段。
- 退出登录放在身份卡内部的橙色浅底描边按钮中，配 `LogoutOutlined`；点击行为和清理范围完全沿用 P1D，不新增确认弹窗或业务分支。
- 我的订单标题旁可显示现有 `orderTotal`；四状态徽标仅在值大于 0 时显示，单个徽标最大展示 `99+`，不得改变筛选枚举和订单统计口径。
- 固定自提点、六项常用服务和底部导航与游客态同构。设计证据用“未选择固定自提点”避免制造演示点位；实际页面必须使用现有接口返回。
- 身份切换或退出后不得短暂显示旧头像、旧名称、旧订单数或旧点位。

## 6. 按钮、卡片与动效状态

| 组件 | 默认 | 按压 | 禁用 / 加载 |
|---|---|---|---|
| 正式主按钮 | 橙色渐变、白字、轻阴影 | `100 ms` 缩放至 `0.98`，底色趋近 `#DC4729`，阴影减弱 | 不透明度 `0.66`，不响应二次点击；加载图标 `800 ms linear` 旋转 |
| 开发体验按钮 | 白底、橙色描边与文字 | 背景 `#FFF7F4` | `#F1F2EF` 背景、`#9AA098` 文字 |
| 取消按钮 | 透明底、灰色描边 | 背景 `#F1F2EF` | 灰色文字和描边，不隐藏 |
| 卡片入口 | 白底 | `80 ms` 过渡到 `#FBFBF8` | 无权限时不灰掉；按 auth intent 进入登录 |
| 退出登录 | `#FFF7F4`、橙色描边 | 背景 `#FFECE6` | 登出处理中禁用，防止重复提交 |

用户开启“减少动态效果”时取消缩放，仅保留底色与不透明度变化。不得添加循环浮动、呼吸、闪烁或装饰性转场。

## 7. 安全区、滚动与响应式边界

- 设计证据使用 `390 × 844 px`。顶部证据预留 `44 px` 状态区和 `44 px` 微信导航区；这两部分由微信原生界面拥有，研发不得自绘时间、胶囊或返回图标。
- “我的”使用微信原生底部导航。设计证据为便于比较保留 `82 px` 底部区域；生产代码不得硬编码该值，应以实际 tabBar 和 `env(safe-area-inset-bottom)` 计算。
- 页面滚动容器从原生导航下沿开始，到原生 tabBar 上沿结束；底部内容需要至少 `16 px + safe-area-inset-bottom` 的可滚动余量。设计证据设置 `18 px` 底部内边距与等效 `scroll-padding-bottom`，在像素取整后保留 `17 px` 可见间距。
- 六项常用服务使游客态和已登录态在 `390 × 844` 下产生**有意的纵向滚动**。顶部画面保留批准原型的内容密度；用户向上滚动后可查看“关于”和“隐私与协议”。不得通过减小字号、缩短行高、缩小触控热区、合并入口或隐藏入口消除滚动。
- 设计证据中的 Profile 可视滚动区为 `674 px`；游客态内容滚动高度为 `766 px`、最大滚动距离 `92 px`，已登录态内容滚动高度为 `746 px`、最大滚动距离 `72 px`。到达最大滚动位置时，两态最后一行下沿与固定 tabBar 上沿均保留 `17 px`。
- 独立登录页没有底部 tabBar，页面内容可滚至系统底部安全区之上；取消返回始终在协议区之后，不做悬浮遮挡。
- 所有横向容器必须 `min-width: 0`；动态单行辅助文案可省略号，用户名称、错误与协议文案必须允许换行。
- 不支持横向滚动。320–430 px 宽度下保持 12–16 px 页面留白、四列订单入口；小于 360 px 时仅缩小列间距，不把订单入口改成两列。

## 8. 可访问性与文案规则

- 触控容器不小于 `44 × 44 px`；紧凑图标必须由父按钮扩大热区。
- 图标同时提供可读名称；箭头和纯装饰图标从辅助技术中隐藏。
- 错误使用文字 + 容器，不以颜色作为唯一表达；认证错误区域使用 `role="alert"` 的等价能力。
- 主次操作不能只靠颜色区分：正式主按钮为实心，开发体验为描边并带“仅本地开发环境”说明，取消为中性描边。
- 页面背景、卡片、文本和图标保持浅色模式；本轮不新增深色主题。系统深色模式下也不得自动反转品牌资产。
- 用户侧业务文案范围保持批准原型与现有 P1D：不新增手机号、账号密码、会员、积分、优惠券、营销承诺或新的隐私授权描述。

## 9. 同视口验收方法

研发完成后，微信开发者工具必须选择同一 iPhone 12/13 视口，并按以下状态截图：

1. 本地 develop + HTTP + demo：独立登录页，开发体验入口可见。
2. 游客打开“我的”：固定自提点未选择；顶部截图展示主要卡片与六项服务的上半部分，再滚动到底补拍“关于”“隐私与协议”和底栏安全间距。
3. 已登录打开“我的”：使用稳定演示账号数据，显示身份、订单数、自提点、常用服务和退出登录；同样补拍滚动到底状态。

QA 先将每张实机图缩放到 `390 × 844 px`，再与本轮对应画面并排。游客态必须同时对照批准原型；不得只比较单张截图或用功能测试替代视觉比较。

允许差异：微信原生状态栏 / 导航胶囊 / 底部安全区、系统字体渲染的细微抗锯齿、真实动态数据长度。
不允许差异：卡片顺序、登录按钮主色与层级、单字 / Emoji 图标、遗漏或合并“开通意向”“关于”等既有入口、游客点位选择被登录阻断、开发体验入口进入正式环境、关键文字被底栏遮挡或横向溢出。

## 10. UI 门禁与未决项

### UI 门禁

`NEEDS REVISION`：六项常用服务的范围与信息架构已关闭，但 iteration-2 实机仍出现服务行被约半宽窄容器压缩的问题；必须完成本节的 profile-only 宽度修复，并按 `390 / 320 / 430 px` 三档复核服务卡、滚动到底和 tabBar 安全距，之后才能重新申请 UI `PASS`。本轮未修改也不要求修改既有橙 / 绿品牌映射、登录页、身份卡或头像。

### 进入研发条件

当前仍保持 `HOLD`，不主动通知研发、不修改 `apps/**`。产品经理需要先向用户确认本规格的服务尺寸边界没有改变待确认的业务规则；确认后，研发只接收 `apps/miniprogram/src/pages/profile/index.wxss`（必要时服务行包装层 `index.wxml`）的样式修复任务，并回传 `390 / 320 / 430 px` 三档顶部与滚动到底证据。未完成该修复和复核前，不得宣称视觉门禁通过。

### 未决 / 可接受差异

1. Figma 原文件不可定位：`BLOCKED`。若后续提供精确 Figma URL 与编辑权限，应在原文件补录这三个状态并回填 node 链接，但不因此推翻本轮视觉决策。
2. 批准原型登录卡有极淡的装饰纹理，未提供独立可用资产；本轮保持纯白卡面，避免截取截图、CSS 图形或手绘 SVG 冒充。该差异不影响信息结构和交互，可由用户选择是否后续补充正式品牌纹理资产。
3. 已登录态没有单独批准原型；身份卡、计数徽标和退出登录为明确标注的最小派生，不新增信息架构或业务规则。
4. 微信原生头部与底部安全区会随开发者工具版本和真机变化，按原生区域差异验收，不要求像素一致。
