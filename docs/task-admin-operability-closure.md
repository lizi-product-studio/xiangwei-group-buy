# TASK-ADMIN-OPERABILITY-CLOSURE

本批以运营后台可操作性为主，并纳入用户实机发现的结算空 JSON 与支付失败恢复缺陷；不改变单一社区团购的订单、支付、退款或配送状态机，也不接入真实支付。

本地预览可在项目根目录执行 `pnpm dev`，同时启动内存 API 与运营后台；需要真实基础设施时仍分别使用 `pnpm dev:api`、`pnpm dev:admin`，不会写入演示业务数据。

## 角色与页面边界

| 角色 | 可见页面/动作 | 失败恢复 |
| --- | --- | --- |
| SUPER_ADMIN | 全部后台页面；配置与紧急动作需二次确认和原因 | 重试、保留草稿、显示 requestId（技术详情折叠） |
| OPERATOR | 商品、分类、区域/点位、团期、运输、差异确认 | 业务错误中文提示；写成功后刷新失败不重复写 |
| CUSTOMER_SERVICE | 售后/取消/通知治理的授权事实 | 只显示授权范围与可恢复状态 |
| FINANCE | 退款、账本及已批准异常 | 仅对批准状态显示执行动作 |
| PICKUP_MANAGER | 已授权点位工作台和到货/核销 | 跨点位 API 仍拒绝，页面显示未授权状态 |

## 状态与数据契约

- 主页面统一使用 `loading → error / empty / ready` 四态；error 不得伪装成 empty 或零值，必须提供重试。
- 网络错误、5xx、401、403、409 与结构化校验详情统一转中文业务文案；不得直出英文异常、HTTP 状态码或内部字段名。
- 所有写操作有 submitting 防重复。写入成功但后续列表刷新失败时，显示“已保存，列表刷新失败，请刷新”，不重新提交写请求；失败时保留表单草稿。
- 分类是后台主数据：可新增、改名、排序、停用；被商品引用时不可硬删除，历史商品/订单继续展示原有事实。停用分类不得被新商品选择。
- 商品保持“一商品一销售规格”；字段以“销售规格（包装单位）”和“默认团期可售量”呈现，产地仍为文本并提供示例。
- 区域由行政目录可搜索选择，运营不手填 `regionCode`；暂停/恢复接单先展示影响并二次确认。
- 团期缺少区域、点位或商品时提供前置引导；切换区域清空旧点位；商品候选展示名称、销售规格、产地，并防止重复选择。
- 到货显示“应到”“正常接收”、短少、破损及未分配数量，四类数量守恒；差异说明必填。差异分配确认前展示受影响订单、顺序和预计退款草案。
- 员工创建、编辑、停用、恢复、重置凭据均有 submitting/catch/中文恢复；角色或点位变化要求原因，一次性凭据仅在创建成功后显示。
- 普通业务页将内部枚举和 ISO 时间映射为中文业务标签/中国本地时间；审计页可在折叠技术详情中保留追踪字段。
- 小程序所有无字段 JSON POST 明确发送 `{}`。订单创建失败只显示普通用户可理解的固定提示；订单已创建但支付失败时保留购物车和结算草稿，允许查看原订单并从详情继续支付，重试不得重新创建订单。

## 验收标准

1. API 不可用时商品、配送、治理、售后等页面明确显示服务不可用/数据加载失败和重试，不显示空表假象。
2. `category` 长度不足在前端拦截且不发 POST，服务端仍拒绝；分类 CRUD、停用引用保护和商品有效分类下拉可重放。
3. POST 成功、GET 刷新失败时只发送一次 POST，显示已保存刷新失败并可恢复。
4. 区域、团期、到货、员工表单的前置关系、数量守恒和权限反例可重放。
5. 375/768/1440 视口主操作可用、无页面级横向溢出。
6. 创建订单失败不跳转虚构订单；创建成功后支付失败只创建一个订单、保留草稿并可进入原订单继续支付，不显示 JSON 或接口错误。

真实 MySQL/Redis、真实微信、生产配置与部署仍是外部门禁；缺少连接 URL 时必须 fail-closed，不以跳过计通过。
