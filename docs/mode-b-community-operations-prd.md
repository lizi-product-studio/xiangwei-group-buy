# Mode B 社区团购运营 PRD

## 文档信息

- **版本：** 1.1
- **状态：** 当前唯一业务基准，待研发与 QA 评审
- **日期：** 2026-08-15
- **适用范围：** 新建 `PLATFORM_COMMUNITY` 团期与订单
- **关联文档：** [人员、权限与运营后台导航 PRD](staff-permissions-and-admin-navigation-prd.md)、[人员创建、权限与导航闭环缺失](product-reflection-staff-account-gap.md)

## 1. 执行摘要

一期不是供应商平台或中心仓系统，而是平台自己经营的“集单—发车—点位交接—用户自提”系统。平台是商品销售、收款、退款和售后的唯一主体；供应商与自提点的合作/费用在线下处理。产品必须让一个非技术运营人员和一个点位负责人完成首团，并在少货、破损、用户取消、逾期未取和品质投诉时留下可执行、可追溯的结果。

## 2. 已冻结的业务边界

### 2.1 日常主线

```text
商品建档 → 创建/发布团期 → 用户付款 → 截单汇总 → 按订单装袋/贴签
→ 人工预约货拉拉并录入发车信息 → 点位负责人现场逐商品确认到货
→ 正常商品开放领取 → 用户出示提货码 → 点位负责人确认领取
```

### 2.2 一期明确不做

- 供应商门户、供应商自动结算、自提点佣金/钱包/提现。
- 中心仓、批次库存、采购单作为社区团期开售或履约的必要前置条件。
- 货拉拉 API、GPS 自动到货、自动判定车辆到达。
- 一团多点、冷链/生鲜、退货再销售、复杂 WMS/ERP。

### 2.3 必须保留的历史边界

历史采购/仓配、撮合和结算数据只读兼容；不得让其字段、菜单或业务规则影响新社区团期。新功能必须按 `PLATFORM_COMMUNITY` 明确分支，不得通过旧订单字段猜测业务模式。

## 3. 角色与权限

| 角色 | 允许做什么 | 明确禁止 |
|---|---|---|
| SUPER_ADMIN | 员工、角色、点位范围、全局运营与紧急代办 | 无；紧急代办必须可审计 |
| OPERATOR | 商品、团期、订单、发车、异常处置、自提点资料 | 到货确认、退款执行、采购成本查看 |
| CUSTOMER_SERVICE | 查询订单、受理和补充售后证据 | 团期/物流配置、退款执行 |
| FINANCE | 支付、批准后的退款、对账与导出 | 商品、团期、物流与点位配置 |
| PICKUP_MANAGER | 已绑定点位的到货确认、现场异常、提货码领取 | 其他点位、全局订单、成本、团期、退款 |

点位负责人必须使用个人账号登录并只看到“点位工作台”。普通运营不能以运单、预计时间或普通按钮代替其现场到货确认；超级管理员仅能紧急代办，并必须留下“代办原因、操作人、时间”的醒目审计。

## 4. 状态模型与展示规则

不要把“车辆状态”“交接结果”“订单可领取状态”混为一个状态。

| 对象 | 状态/事实 | 用户可见含义 | 后台下一步 |
|---|---|---|---|
| 配送 | 待发车 / 运输中 | 车辆尚未由点位确认 | 录入发车 / 等待点位确认 |
| 点位交接 | 已确认且无差异 | 已到货 | 等待用户领取 |
| 点位交接 | 已确认且有差异 | 已到货（有差异） | 处理配送异常；正常商品已可领取 |
| 订单行 | 可领取 / 部分已领 / 已领取 | 展示本商品可领、已领和异常数量 | 提货码确认领取 |
| 订单行 | 异常待处理 / 已退款 | 展示异常原因和退款进度 | 运营处理 / 财务执行 |

车辆到达现场不等于系统到货。只有已激活且绑定本点位的负责人提交“每个商品应到 = 实到 + 短少 + 破损 + 拒收”的现场事实后，系统才更新交接结果、开放正常数量的提货码，并创建异常任务。若预计到达时间已过但未确认，后台只显示“待点位确认已逾期”，不得自动改为已到货。

## 5. 本轮必须补齐的功能

### Epic A：到货差异状态（当前研发中）

**目标：** 让运营、点位与用户正确理解“到货”和“有差异到货”。

- 物流列表必须从交接事实读取差异结果；有短少、破损、拒收或错点时显示“已到货（有差异）”，不能只显示“已到货”。
- 无差异时，运营端下一步为“等待用户领取”；有差异时为“处理配送异常”，并明确正常商品可领取。
- 点位负责人只处理实到的正常数量；差异事实不可由点位负责人退款或改写。
- 必须覆盖无差异、有差异、跨点位拒绝、重复确认和超级管理员紧急代办审计。

### Epic B：已付款订单取消与用户售后闭环

**问题：** 未支付订单可取消，但已付款订单目前无法走社区模式的自助取消/售后闭环；这会让用户资金和客服处理卡住。

**规则：**

1. 未支付订单：用户可直接取消；库存/可售量只释放一次。
2. 已付款且未截单：用户可自助取消，系统原路全额退款；取消与支付回调竞争时，必须只产生一个最终资金结果。
3. 截单后至提货前：不提供自动取消；用户可提交“取消申请”，客服/运营按事实决定，财务执行。
4. 交接短少、破损、拒收、错点：由点位登记事实 → 运营确认受影响订单行和数量 → 财务按**订单行成交快照价 × 已确认异常数量**原路部分退款。正常商品继续领取，退款绝不自动回补可售量。
5. 提货后的品质问题：用户可在提货后 **24 小时** 内，按订单行和数量提交原因、图片/说明；客服受理、运营决定驳回或部分/全额退款、财务执行。首期不做食品退回和二次销售。
6. 退款总额不得超过该订单已实付金额；同一异常/售后重复提交或重试不得重复退款。

**验收：** 用户在小程序能看到“可取消/申请售后/处理中/已退款/已驳回”的准确入口和结果；后台能从申请看到订单行、数量、证据、处理意见和退款依据；不能把社区订单导入旧模式整单退款入口。

### Epic C：装袋/贴签与异常分配

**目标：** 避免点位负责人临场决定“哪位用户少一件”。

- 团期截单后，订单管理提供按自提点导出的拣货清单和“每订单一包”的装袋/标签清单，至少包含订单号尾号、提货码关联标识、商品及数量；标签不展示完整手机号或支付信息。
- 发车前运营按该清单完成装袋/交接。此功能只是履约辅助，不建立仓库、入库、批次或库存账。
- 出现差异后，系统按已确认交接数量生成受影响订单行和数量清单；运营可在受控页面确认分配，不能由点位负责人任意挑选用户。
- 分配完成后，正常数量继续领取，受影响数量进入退款/补送待处理。

### Epic D：提货期限与逾期未取

**默认决策：** 团期创建时设置提货起止时间，默认到货后 3 个自然日；用户到货当日和截止前 1 日各收到一次提醒。

- 截止前可正常核销；截止后订单进入“逾期待处理”，不自动退款、不自动报损、不自动改为已领取。
- 运营可以为订单人工延长一次，或在核实后决定退款/报损并记录原因；点位负责人只能登记“仍在点/无法联系”等事实，不能自行处置资金或货物。
- 小程序必须在订单页和通知中展示自提点、起止时间和逾期结果；点位工作台必须突出当日/逾期订单。

### Epic E：通知、延误和人工兜底

- 事件至少包括：已发车、已到货可领取、到货有差异的受影响说明、部分退款完成、提货截止提醒、逾期待处理。
- 每次通知必须有订单、事件、尝试次数、最终状态和失败原因；订阅消息未授权或发送失败时进入运营/客服的“待人工通知”队列。
- 预计到达已逾期而未点位确认时，只对运营创建“联系司机/点位”待办；不得给用户发送“已到货”。
- 通知文案不得承诺尚未发生的到货、退款或补送。

### Epic F：现场证据的受控采集

- 点位交接差异和用户品质售后都支持上传照片及文字说明；不得要求现场人员把任意外部 URL 当作证据。
- 附件应记录上传人、时间、关联订单/交接/售后；仅相关角色可见，链接应受权限保护。
- 研发需选定受控文件存储、文件类型/大小限制、恶意文件检测和保留期限；这是一项外部依赖，不得伪造为已具备。

## 6. 体验与页面归属

| 页面 | 应完成的工作 | 不应出现 |
|---|---|---|
| 商品管理 | 长期商品资料、启停、受限采购备注 | 发车、到货、团期发布 |
| 团期管理 | 选择商品、售价/数量、开售/截单/提货窗口、固定自提点、发布 | 商品主数据编辑、物流操作 |
| 订单管理 | 检索订单、进度、取消/售后、拣货/装袋/标签导出 | 创建团期、直接退款执行 |
| 物流管理 | 运单/司机/车牌/ETA、发车、交接状态、延误待办 | 商品列表、新增商品、创建团期 |
| 自提点管理 | 地址、营业/提货时间、启停、负责人绑定 | 点位佣金/钱包 |
| 售后与异常 | 异常事实、影响订单行、处理决定 | 点位负责人退款 |
| 财务管理 | 退款执行、支付/退款对账 | 现场确认、异常分配 |
| 点位工作台 | 本点到货、待领取、提货码、现场事实 | 全局后台和资金数据 |

## 7. 研发顺序与发布门槛

1. 完成 Epic A，并由 QA 复测状态、角色和并发路径。
2. 完成 Epic B 的已付款取消与社区售后/部分退款链路，先保证资金和幂等性。
3. 完成 Epic C 的装袋标签与受影响订单行分配，避免线下公平性靠人工记忆。
4. 完成 Epic D/E 的提货期限、延误待办和通知兜底。
5. Epic F 在文件存储和安全方案明确后实施；没有受控证据能力时，不可把“上传证据”列为已上线功能。

每个 Epic 都必须有：服务端权限校验、并发/重复提交保护、审计记录、异常/空/加载状态、桌面与小屏验证，以及独立 QA 的核心流程复测。真实支付、微信订阅消息、文件存储、MySQL/Redis 仍需在预发布环境提供单独证据；没有证据不能标记为 Release PASS。

## 8. 非目标与开放项

- 不因本 PRD重启采购与中心仓模块，也不重做历史订单。
- 首期的“补送”只记录运营决定和人工线下执行结果；不自动创建新配送路线。
- 24 小时品质售后期与 3 天提货期是本轮默认运营政策；上线前由负责人确认是否调整。若调整，只改政策配置与文案，不改变“事实登记—运营决定—财务退款”的职责边界。
- 证据附件的对象存储、保留期限和食品合规话术需要研发、安全和运营共同确认。
