# MySQL runtime and migration privilege split

The current online service uses `hometown@%` and has schema-wide `ALL PRIVILEGES`, including DDL. `apps/api/src/modules/core/mysql-store.ts` performs runtime reads/writes against `community_product_state` and, when enabled, `community_entity_records`, `community_entity_relations`, `community_entity_sequences`, and `community_entity_store_state`. Runtime code does not apply SQL migrations. The separate `apps/api/src/scripts/migrate.ts` applies files under `infra/mysql/migrations`, creates `schema_migrations`, takes a named migration lock, and records results. The entity-store migration tool additionally uses `community_entity_migration_journal`, `community_legacy_snapshots`, and `community_entity_reverse_exports`.

`runtime-grants.sql` is the proposed production-account minimum CRUD grant set. It revokes only schema-scoped privileges for the existing account and restores table-scoped SELECT/INSERT/UPDATE/DELETE. It grants no DDL, file, trigger, event, or grant-option authority. Do not run it on a production database before the isolated matrix and rollback path pass. Preserve exact `SHOW GRANTS FOR 'hometown'@'%';` output under the restricted deployment evidence directory before any approved change. `runtime-grants.template.sql` is pinned to the disposable Stage B schema and exists only to test the same privilege shape with a test-only account. `rollback-runtime-grants.sql` restores the currently observed schema-wide grant; it is a candidate rollback, not evidence that production changed.

The migration template is intentionally bound to `hometown_sec_b_20261010` and a separately supplied test-only account. It grants CRUD only on that isolated schema and CREATE/INDEX/CREATE TEMPORARY TABLES only on that isolated schema. It does not grant permanent DROP or ALTER. The runner must prove the current five migration files can be applied with these grants, including migration-journal DML. If MySQL requires an additional privilege (especially for dropping session temporary tables), stop and narrow the migration operation rather than granting permanent schema DROP without review.

Required isolated matrix, using MySQL 8.4 with `hometown_sec_b_20261010` only:

1. With the candidate runtime grants, exercise the real API store's representative reads and writes over synthetic users, orders, payments, refund/notification rows, ledger rows and audit rows. Exercise both `LEGACY` and `ENTITY` persistence modes where the runner can do so without importing user data.
2. As the runtime account, assert SELECT/INSERT/UPDATE/DELETE on each runtime-owned table work. Assert CREATE TABLE, ALTER TABLE, CREATE INDEX, DROP TABLE, TRUNCATE and DDL in any other schema fail. Keep all DDL probes inside disposable test schemas.
3. As the migration account, run all current migrations twice and verify the second run is an idempotent no-op. Prove the expected temporary-table path and migration journal DML work. Assert CREATE outside the test schema and permanent DROP fail.
4. Stop/remove only the disposable test schema and test-only accounts after retaining sanitized results. Never reuse the production schema name, production credentials, data volume or `hometown` production account in this matrix.

No permission change or grant SQL is applied to the production account by this candidate. Production account separation still requires a distinct already-authorized migration identity/configuration; this task does not create a production password or change `.env`.
